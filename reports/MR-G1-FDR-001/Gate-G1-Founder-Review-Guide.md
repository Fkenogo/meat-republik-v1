# Gate G1 Founder Review Guide

**Pack ID:** MR-G1-FDR-001

**Purpose:** Provide a practical sequence for genuine Founder review of Gate G1
conditions.

## Before Review

1. Read the Executive Summary and Gate G1 Current State in the
   [Founder Decision Pack](Gate-G1-Founder-Decision-Pack.md).
2. Confirm that the pack is decision support, not a constitutional amendment.
3. Use the [Condition Register](Gate-G1-Condition-Register.md) to identify which
   decisions affect blocking conditions.
4. Do not treat a recommendation as an approved disposition.

## Founder-Input Rules

- Founder observations and rationale must be genuine Founder-origin input.
- The agent must not fabricate, complete, paraphrase into approval, or infer
  Founder rationale.
- Blank disposition fields remain blank until the Founder supplies a decision.
- Silence, document preparation, repository presence, or a recommendation does
  not imply approval.
- An effective date must not be inferred from a meeting date, commit date, file
  date, or review date.
- Conditional approval must name every accepted condition, closure owner, and
  required closure evidence.

## Recommended Review Sequence

### 1. Enterprise Primary-Parent Chain

Review FDR-G1-001 first because it determines how later classifications trace
authority.

Founder should record:

- selected Option A, B, C, or a Founder-authored alternative;
- one primary parent for every non-root enterprise artefact;
- permitted use of `Derived From` and `Related Authority`;
- rationale for precedence and conflict resolution.

Do not proceed as if MR-GOV-001 has authority until this relationship is clear.

### 2. Classification Model

Review FDR-G1-002 for CX-001 and the A1/A2/B1 distinctions relevant to domain
constitutions.

Founder should record:

- whether a domain constitution is A2;
- CX-001's class and authority level;
- whether its current title remains;
- which downstream Experience frameworks and standards it may authorize.

### 3. Brand-Family Derivation

Review FDR-G1-003 using the classification principles selected in step 2.

Founder should record:

- whether BC-001 remains B1 or becomes A2;
- whether BF-001 and BE-001 are parent/child or sibling frameworks;
- whether same-level derivation is permitted;
- any rule or exception that future families may rely on.

### 4. MR-GOV-001

Review FDR-G1-005 after the enterprise parent and classification models are
known.

Founder should record:

- document or programme treatment;
- canonical identifier label;
- authority level and primary parent;
- repository domain and document family;
- title treatment;
- approval lifecycle.

### 5. Canonical Metadata Schema

Review FDR-G1-004 and the
[Proposed Metadata Disposition Matrix](Proposed-Metadata-Disposition-Matrix.md).

Founder should record:

- approved fields, formats, cardinality, and responsible authorities;
- approved lifecycle vocabulary;
- which recommended artefact values are accepted, changed, or deferred;
- which fields are genuinely not applicable;
- whether migration is a condition before Gate or controlled post-Gate work.

No version, status, authority, approval, or date should be inserted merely to
complete the table.

### 6. Governance Registers

Review FDR-G1-006 only after MR-GOV-001 and metadata decisions establish the
registers' authority and schema.

Founder should record for each register:

- authorized or deferred;
- authority and classification;
- primary custodian;
- initial population scope;
- historical evidence rule;
- validator relationship;
- effective date.

No register should be populated with reconstructed approval history.

### 7. Legacy Dispositions

Review FDR-G1-007 with the
[Legacy Working Draft Inventory](Legacy-Working-Draft-Inventory.md).

Founder should record:

- overall disposition strategy;
- item-by-item exceptions;
- treatment of MR-BF-001 and MR-BF-002 duplicate legacy identifiers;
- relationship of MR-BF-000 to FCDP-001;
- which files require content reconciliation before archive;
- any governed archive path and move authority.

No bulk move should occur before these dispositions are recorded.

### 8. Gate G1 Outcome

Review the [Condition Register](Gate-G1-Condition-Register.md) after all seven
decisions.

Select one outcome:

- **Outcome A — Gate G1 Approved:** all blocking conditions resolved and
  governance activation requirements satisfied.
- **Outcome B — Gate G1 Approved with Conditions:** every remaining condition
  explicitly accepted, with a closure owner and defined evidence, and no
  unusable authority contradiction.
- **Outcome C — Gate G1 Deferred:** classification, authority, metadata, or
  governance remains too ambiguous for controlled approval.

The agent must not select the outcome.

## Decision Recording Checklist

For every FDR, confirm the Founder personally supplied:

- [ ] disposition;
- [ ] rationale;
- [ ] accepted or imposed conditions;
- [ ] effective date, if applicable;
- [ ] closure responsibility;
- [ ] closure evidence.

For Gate Outcome B, additionally confirm:

- [ ] each open condition is named by ID;
- [ ] the Founder expressly accepts each named condition;
- [ ] no open authority contradiction makes the model unusable;
- [ ] a closure owner is assigned;
- [ ] a closure evidence requirement is written;
- [ ] a review or due date is recorded where required.

## After Founder Review

1. Preserve the Founder-origin decision record verbatim.
2. Validate that every disposition maps to a condition and affected artefact.
3. Prepare a separate governed remediation plan.
4. Do not amend constitutional artefacts until the Founder expressly authorizes
   implementation.
5. Re-run constitutional integrity and traceability validation after every
   authorized remediation.
6. Record Gate closure only after the selected outcome's evidence test passes.
